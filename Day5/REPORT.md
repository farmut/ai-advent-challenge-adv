## Как работал агент

Для каждой задачи агент выбирал профиль:
- **«Поиск бага»** (5 задач): Reproduce → Diagnose → Fix → Validation → Report;
- **«Бизнес-фича»** (10 задач: фичи, рефакторинг, тесты, документация): Research → Executing → Validation → Report.

- **Reproduce.** Перед диагностикой баг воспроизводился временным тестом, а не выводился из описания.
- **Diagnose / Research.** Консилиум субагентов запускался параллельно: архитектор (Go), безопасность, DevOps, отладчик; UI-дизайнер — только для текстов ответов бота. Когда мнения расходились, решение принимал оркестратор и записывал обоснование.
- **Fix / Executing.** Код писал отдельный субагент-исполнитель (Go).
- **Validation.**
  - Проверки: сборка, `go vet`, `gofmt`, `go test -race`, покрытие и diff со снимком кода до задачи (так проверялось, что изменены только разрешённые файлы).
  - E2E: собранный бинарник запускался против поддельных Telegram и OpenWeatherMap на localhost, без сети и реальных токенов.

## Решения, которые агент принял сам

1. **T02.** Имя бота берётся у Telegram (`getMe`) при старте, а не из переменной окружения. Если имя задавать в env, оно разойдётся с реальным после переименования бота.
2. **T04.** Задача противоречила сама себе: тест, который по условию должен был остаться зелёным, проверял само ошибочное поведение. Вход теста изменён, смысл проверки сохранён.
3. **T05.** Правила проекта описывали старый набор символов для названия города. Агент не стал править файл правил (это инструкции владельца) и вынес обновление в рекомендации.
4. **T07.** Безопасник предлагал хранить последний город в нормализованном виде, а задача T11 запрещает нормализацию в delivery-слое. Решение: хранить ввод пользователя, но не длиннее 512 байт — так память ограничена, а правило не дублируется.
5. **T11.** Текст ошибки «город не найден» не содержит названия города, чтобы ввод пользователя не попадал в логи.
6. **T13.** Агент нашёл противоречие в критериях и не стал ради покрытия править продакшен-код, хотя задача это запрещала.
