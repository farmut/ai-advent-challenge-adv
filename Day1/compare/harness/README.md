# Black-box harness для Telegram-бота погоды (Day1, варианты A и B)

Стенд собирает бинарь варианта из `Day1/variant-<v>/src` и запускает его как есть, без правок кода. Вместо настоящих Telegram и OpenWeatherMap бот общается с фейковыми серверами стенда. Используется только стандартная библиотека Go.

## Запуск

Команды выполняются из корня репозитория.

```sh
# прогон одного варианта (до 4 мин) -> Day1/compare/transcripts/{a.json,a-bot.log}
go -C Day1/compare/harness run . -variant a
go -C Day1/compare/harness run . -variant b      # или -variant all

# HTML в стиле Telegram + PNG через headless Chrome
go -C Day1/compare/harness run ./cmd/render -screenshots
```

Флаги `run .`:

- `-bindir` — куда класть бинари, сырые логи (`<v>-bot.raw.log`, `<v>-harness.log`) и CA. По умолчанию `$TMPDIR/weatherbot-harness`.
- `-wait` — сколько ждать ответа в обычном сценарии, по умолчанию 5 с.
- `-no-docker` — не пробовать запуск в контейнере.

Что нужно: Go 1.26, для варианта A ещё Docker с образом `alpine:latest`. Для `-screenshots` нужен Google Chrome.

## Как бот направляется на фейки

1. **env.** Стенд выставляет `TELEGRAM_BOT_TOKEN=123456:TEST_FAKE_TOKEN_abcdef`, `OPENWEATHER_API_KEY=TEST_OWM_KEY_123` и base URL обоих фейков под всеми найденными именами. Имена берутся из строковых литералов `*_URL` в исходниках плюс распространённые варианты (`TELEGRAM_BASE_URL`, `OPENWEATHER_BASE_URL`, …). Одновременно `HTTPS_PROXY`/`HTTP_PROXY` указывают на прокси-предохранитель стенда в режиме deny. Если бот игнорирует base URL, он не уйдёт в настоящий интернет, а цель попытки запишется. Если за 10 с к фейку Telegram не пришло ни одного запроса, в транскрипт пишется «не тестируемо black-box: base URL не подменяется».
2. **Нативный `HTTPS_PROXY` + MITM.** Прокси подхватывается, но на macOS Go проверяет TLS через системное хранилище, а `SSL_CERT_FILE` игнорирует. Рукопожатие падает, и это фиксируется в `attempts`.
3. **Docker.** Тот же исходник собирается под linux и запускается в `alpine` с `HTTPS_PROXY=http://host.docker.internal:<port>` и `SSL_CERT_FILE` с одноразовым CA стенда. Прокси терминирует TLS для `api.telegram.org` и `api.openweathermap.org` и передаёт запросы фейкам. Код и бинарь не меняются, подменяется только окружение. Вариант A проходит именно так: base URL у него зашит в коде.

## Фейки

- **Telegram** (`internal/fake/telegram.go`):
  - `getUpdates` по очереди отдаёт апдейты с растущими `update_id` и учитывает `offset`. Пустой long-poll держится около 1 с. Параметры принимаются из query, JSON и form.
  - `sendMessage` записывает `chat_id`, `text` и `parse_mode`.
  - `getMe` отдаёт профиль бота, остальные методы отвечают `{"ok":true,"result":true}`.
  - При неверном токене отвечает 404, как настоящий API.
- **OpenWeatherMap** `/data/2.5/weather` (`internal/fake/owm.go`):
  - Москва/Moscow и London → 200 с реалистичным JSON.
  - Nowhere → 404, Error500 → 500, RateLimit → 429.
  - Неверный `appid` → 401.
  - Slow → 200 через 25 с. Huge → 200 и около 50 MiB «JSON» с одной бесконечной строкой, чтобы проверить ограничение размера тела.
  - Для каждого запроса записываются raw query, все значения `q` и `appid`, статус, число отданных байт и обрыв клиентом.

## Сценарии и проверки

Сценарии 1–13 идут из чата 1001 с паузой не меньше 2,2 с между сообщениями. Вариант B ограничивает чат одним запросом в 2 с, а эти сценарии проверяют функциональность, а не лимит. Список сценариев:

1. `/start`
2. `/help`
3. `Москва`
4. `/weather London`
5. `/weather` без города
6. `Nowhere`
7. `Error500`
8. `RateLimit`
9. `a&appid=x#` — инъекция. Проверяется, что в OWM ушёл ровно один `appid` с верным ключом и `q` в точности равен вводу, либо что запрос отклонён до OWM.
10. 500 символов «а»
11. `Slow` — время до ответа, ожидание до 40 с
12. `Huge`
13. `/weather@WeatherBot Москва`
14. flood: 20 × «Москва» одним батчем из чата 2002. Считается, сколько запросов ушло в OWM и сколько ответов пришло.
15. Отдельный процесс бота с неверным ключом, сообщение «Москва» (OWM отвечает 401).

Для каждого сценария в JSON пишутся вход, все `sendMessage` со временем от выдачи апдейта, запросы в OWM и флаги: `replied`, `leak_in_reply`, `injection`, `expect` (соответствует ли ожидаемому поведению).

- **Утечки.** В сыром stdout/stderr бота и в текстах ответов считаются вхождения `TEST_FAKE_TOKEN` и `TEST_OWM_KEY` (`leaks`). Только после подсчёта в коммитуемом `transcripts/<v>-bot.log` секреты заменяются на `<TOKEN>`, `<KEY>` и `<WRONG_KEY>`.
- **Graceful shutdown.** После сценариев процесс получает SIGTERM. Если он сам завершился за 5 с с кодом 0, `graceful=true`, иначе SIGKILL. Для Docker в `elapsed_ms` входит и задержка `docker kill`.

## Рендер

`cmd/render` читает `transcripts/{a,b}.json` и пишет `chat-a.html`, `chat-b.html` и `chat-side-by-side.html`. Сообщения пользователя показаны справа синим, ответы бота слева серым. Над группами стоят заголовки сценариев, под ними отметки ✓/✗: ответ, ожидаемое поведение, утечки, инъекция. Текст экранируется через `html/template`.

С `-screenshots` Chrome снимает страницу окном высотой 16000 px, после чего PNG обрезается по фону. Если страница не помещается, она делится на `-part1`/`-part2`.
